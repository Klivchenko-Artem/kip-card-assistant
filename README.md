# Черновики карточек для приборов КИП

Прототип сервиса: на вход данные о приборе, на выход черновик карточки для B2B-магазина. В черновике SEO-заголовок, SEO-описание, ключевые характеристики, поисковые запросы и подсказка для менеджера. Текст пишет LLM, а проверяет его код, потому что главный риск здесь в выдуманных характеристиках.

## Установка и запуск

Нужен Python 3.11 или новее и бесплатный ключ Groq: https://console.groq.com/keys

```
python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # Linux, macOS
pip install -r requirements.txt
cp .env.example .env            # Windows: copy .env.example .env
```

В `.env` впишите свой `GROQ_API_KEY`. Файл добавлен в `.gitignore`, в коде ключа нет.

Веб-форма:

```
uvicorn app.main:app --port 8000
```

Откройте http://127.0.0.1:8000. Данные можно ввести по полям или вставить JSON. У каждого блока результата есть кнопка копирования, плюс кнопка для всей карточки в Markdown.

API:

```
curl -X POST http://127.0.0.1:8000/api/card --data-binary @examples/input/testo-510.json
```

Командная строка, результат сохраняется в `.json` и `.md`:

```
python -m app.cli examples/input/testo-510.json --out examples/output
```

Тесты работают без ключа и без сети:

```
python -m pytest
```

## Формат входа

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {"диапазон измерений": "0-1,6 МПа", "присоединение": "G1/2"},
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

## Что в ответе

- `status`: `ready`, если все проверки пройдены, или `needs_review`, если есть замечания или противоречия в данных. Простое отсутствие параметра статус не меняет, оно показано в `missing_data`.
- `card`: сама карточка.
- `missing_data`: что отсутствует или требует уточнения, включая противоречия в исходных данных.
- `warnings`: что не прошло проверку и что надо посмотреть глазами.
- `markdown`: вся карточка одним текстом.

Если нет названия либо нет сразу и характеристик, и описания, сервис вернет ошибку 422 и не пойдет в модель: писать не из чего. На некорректный JSON ответ тоже 422 с указанием строки и символа. Ошибки API модели приходят как 502 или 503 с понятным текстом.

## Примеры

Готовые результаты лежат в `examples/output`, входные данные в `examples/input`.

| Товар | Откуда | Зачем |
| --- | --- | --- |
| Дифференциальный манометр testo 510 | фид, оффер 58444 | полные данные |
| Измеритель-регулятор ТРМ1-Щ5.У2.С | фид, оффер 235490 | много характеристик, в данных есть противоречие |
| Манометр DM 02 | пример из задания, сокращенный: класс точности очищен, диаметр корпуса убран | неполные данные |

В фиде у товаров есть только название, тип, производитель, цена и артикул. Характеристик и описаний там нет, поэтому я написал `scripts/fetch_product.py`: он берет товар из фида по id и забирает данные со страницы товара, на которую фид ссылается.

```
python scripts/fetch_product.py 58444 --out examples/input/testo-510.json
```

## Как устроены промпты

Текст промптов лежит в `app/prompts.py`.

Системный промпт задает роль редактора B2B-магазина и одно главное правило: единственный источник фактов это входной JSON. Отдельно запрещено переводить единицы, дополнять данные знаниями о серии, упоминать ГОСТ, сертификаты, поверку и гарантию, если их нет во входе, и писать штампы без фактов. Для каждого поля описано, что в нем должно быть. Входной JSON назван данными, а не инструкциями, чтобы текст из паспорта не мог поменять задачу.

Ответ модели идет строго по JSON-схеме (structured outputs), поэтому разбирать свободный текст не приходится.

Если черновик не прошел проверки, модель получает список конкретных замечаний и переписывает его, максимум два раза (`MAX_REWRITES`). Сервис оставляет лучшую попытку. Если замечания остались, они показываются в блоке "Проверить вручную".

## Решения

Значения характеристик модель не пишет вообще. Она выбирает ключи из `specs`, а подпись и значение строки подставляет код. Поэтому в таблице характеристик выдуманного значения появиться не может. Ключ модель все же может выбрать неудачно, такая строка окажется лишней, но не ложной.

Пять параметров из задания (диапазон, точность, питание, корпус, интерфейсы) есть в карточке всегда. Если для них нет ключа, в строке стоит "данных нет", а параметр попадает в `missing_data`. Остальные характеристики модель подбирает под тип прибора, для нужного, но отсутствующего параметра она ставит `null`.

В свободном тексте полной гарантии нет, поэтому после модели работает проверка в `app/checks.py`:

- Число с единицей должно быть во входных данных именно в такой паре. Так ловятся и выдумка, и пересчет: 1,6 МПа нельзя заменить на 16 бар.
- Числа без единиц и латинские обозначения (RS-485, IP54) тоже ищутся во входе.
- Упоминания ГОСТ, сертификатов, поверки, гарантии и доставки допустимы, только если они есть в исходных данных.
- Свойства вроде "надежный" и "компактный" и типовые области применения тоже сверяются со входом.
- Длины заголовка и описания и число запросов считает код. Если описание вышло длиннее 1200 символов, лишние предложения в конце убираются целиком.
- В каждом поисковом запросе должен быть тип прибора или модель.

Сознательное отступление от задания: если значения `specs` и описание вместе короче 300 символов, минимум в 800 символов снимается. Пробные запуски показали, что на таком входе модель добирает объем выдумкой, а запрет на выдумку в задании важнее объема. Текст выходит коротким, карточка получает `needs_review` и просьбу дополнить данные.

Модель `openai/gpt-oss-120b` через Groq я выбрал из-за строгой JSON-схемы и бесплатного тарифа: проверяющему не нужно ничего оплачивать. В `GROQ_MODEL` можно указать другую модель Groq, но она должна поддерживать строгую JSON-схему и параметр `reasoning_effort`.

CMS, админ-панели, базы данных и деплоя нет, как и просили в задании.

## Сложности

В данных сайта встречаются противоречия. На странице ТРМ1-Щ5.У2.С глубина корпуса 102 мм в коротком блоке и 103 мм в описании и таблице, в описании указан порт USB Type-C, а в характеристиках "без интерфейса". Промпт просит выносить такое в блок "Уточнить" и не использовать спорное значение в тексте, но это работа модели, а не проверка кодом, поэтому она может что-то пропустить. В примере ТРМ1 расхождение 102 и 103 мм как раз пропущено: в тексте 103, в таблице 102.

На моем ключе Groq лимит 8000 токенов в минуту, а один запрос с рассуждениями модели съедает большую его часть. Поэтому переписывание иногда ждет лимит, каждое ожидание занимает до 65 секунд, а на всю карточку отведено 4 минуты. Есть и суточный лимит в 200 000 токенов, при настройке промпта я в него упирался. Клиент учитывает заголовок `retry-after`, а если лимит кончился на этапе переписывания, отдает уже готовый черновик с замечаниями.

## Ограничения

- Проверка ловит числа, единицы и обозначения, но не смысл. Фразу вроде "подходит для агрессивных сред" без числа она пропустит, если этого слова нет в списке. Поэтому результат это черновик, и его читает человек.
- Знак числа не проверяется: -50 и +50 для проверки одно и то же.
- Проверка не видит неверного сочетания верных чисел. В примере ТРМ1 модель написала диапазон от -40 до +2500 °C: оба числа есть во входе, но -40 это температура воздуха, а не датчика. Примеры я руками не правил, это честный вывод сервиса.
- Похожие латинские и русские буквы считаются разными: AAA латиницей при "ААА" кириллицей дает ложное замечание.
- Список слов для проверки свойств и областей применения составлен вручную и неполный. Возможны и ложные срабатывания, они попадают только в замечания.
- Модель плохо считает символы, поэтому попадание в длину часто требует переписывания.
- `fetch_product.py` привязан к текущей верстке сайта. Страница товара иногда общая для серии, тогда данные относятся к серии, а не к конкретной модификации.
- Результат зависит от модели и может отличаться между запусками.

## Что можно улучшить

- Второй проход модели как независимого проверяющего: сверка каждого утверждения текста с исходными данными.
- Свои наборы обязательных характеристик для разных типов приборов (манометр, датчик, регулятор).
- Разбор PDF с паспортами, ссылки на них есть на страницах товаров.
- Пакетная обработка фида с очередью и учетом лимитов.
- Набор эталонных карточек для замера качества при смене промпта или модели.
